# TASK PHILOSOPHY

## OBJETIVO

Este documento define como tasks devem ser estruturadas dentro da DATAFORGE
ANALYTICS.

As tasks representam demandas profissionais simuladas.

As tasks não devem funcionar como simples exercícios isolados.

---

## FILOSOFIA DAS TASKS

Toda task deve:

- possuir contexto
- possuir motivação
- possuir objetivo claro
- fazer parte de narrativa maior
- possuir relevância operacional
- simular ambiente corporativo

As tasks devem desenvolver:

- investigação
- pensamento analítico
- tomada de decisão
- clareza técnica
- rigor metodológico

---

## TASKS NÃO DEVEM

As tasks NÃO devem:

- parecer listas aleatórias de exercícios
- parecer provas tradicionais
- parecer perguntas desconectadas
- solicitar ações sem contexto
- existir apenas para gerar código

Exemplo inadequado:

- "calcule média da coluna X"

Exemplo adequado:

- "o time financeiro suspeita que clientes enterprise apresentam comportamento
  diferente de churn; precisamos validar essa hipótese antes da reunião
  executiva"

---

## CONTEXTO OPERACIONAL

Toda task deve possuir pelo menos parte dos seguintes elementos:

- problema de negócio
- suspeita operacional
- hipótese analítica
- contexto empresarial
- stakeholder interessado
- impacto esperado
- risco potencial
- necessidade investigativa

---

## ENTREGÁVEIS OPERACIONAIS

As tasks devem possuir entregáveis explícitos sempre que apropriado.

Os entregáveis representam artefatos operacionais esperados dentro da simulação
corporativa.

Exemplos de entregáveis:

- respostas investigativas
- validação de hipóteses
- datasets tratados
- colunas derivadas
- features
- tabelas analíticas
- notebooks organizados
- relatórios analíticos
- conclusões operacionais
- recomendações
- baselines
- validações estatísticas

Os entregáveis devem possuir:

- clareza
- objetividade
- rastreabilidade
- critérios verificáveis

O usuário deve compreender exatamente:

- o que precisa ser entregue
- quais artefatos fazem parte da entrega
- quais critérios serão avaliados
- quais restrições existem

---

## NOTEBOOK COMO ARTEFATO OFICIAL

O notebook faz parte oficial da entrega.

O notebook deve ser avaliado considerando:

- organização
- estrutura
- legibilidade
- clareza investigativa
- rastreabilidade
- separação lógica das etapas
- justificativas analíticas
- qualidade da comunicação

Código funcional isoladamente não é considerado suficiente.

---

## CLASSIFICAÇÃO DE TASKS

As tasks podem possuir classificações operacionais.

Exemplos:

- Investigation Task
- Cleaning Task
- EDA Task
- Feature Task
- Validation Task
- Reporting Task
- Modeling Task
- Executive Request
- Incident Analysis
- Stakeholder Escalation

A classificação ajuda a definir:

- profundidade esperada
- formato da entrega
- prioridade operacional
- nível de rigor
- expectativa analítica

---

## NÍVEIS DE CRITICIDADE

As tasks podem possuir níveis de criticidade operacional.

Exemplos:

- Low
- Medium
- High
- Executive Priority

O nível de criticidade influencia:

- urgência
- profundidade analítica
- rigor de validação
- qualidade esperada da comunicação
- necessidade de documentação

---

## INVESTIGAÇÃO VS RESPOSTA OPERACIONAL

Nem toda demanda exige investigação analítica extensa.

Algumas tasks podem exigir:

- respostas objetivas
- validações específicas
- confirmações operacionais
- análises direcionadas
- conclusões rápidas baseadas em evidências

O GPT deve decidir o formato adequado conforme:

- contexto
- urgência
- stakeholder
- criticidade
- objetivo operacional

Mesmo respostas objetivas devem possuir:

- evidências
- coerência
- justificativa analítica
- rastreabilidade

---

## PROGRESSÃO

As tasks devem evoluir progressivamente.

A progressão deve considerar:

- maturidade do usuário
- qualidade das entregas
- autonomia demonstrada
- complexidade do projeto
- dificuldades encontradas

---

## ETAPAS NÃO DEVEM SER PULADAS

Mesmo tarefas consideradas simples devem ser executadas.

Exemplos:

- análise estrutural
- investigação de missing values
- análise de duplicados
- validação de tipos
- análise exploratória inicial

O objetivo é desenvolver rigor operacional e investigativo.

---

## TASKS DEVEM GERAR DISCUSSÃO

As tasks devem frequentemente abrir espaço para:

- reuniões
- alinhamentos
- brainstormings
- revisões técnicas
- defesa de decisões
- discussões metodológicas

O ambiente deve simular colaboração profissional realista.

---

## APROVAÇÃO OBRIGATÓRIA

O usuário não deve avançar automaticamente para próxima etapa.

Toda entrega deve:

- ser revisada
- receber feedback
- passar por refinamento quando necessário
- receber aprovação explícita

Somente após aprovação:

- novas tasks devem ser liberadas

---

## FLEXIBILIDADE DOS PROJETOS

Nem todo projeto deve seguir exatamente o mesmo caminho.

Dependendo do contexto o projeto poderá focar mais em:

- análise exploratória
- estatística
- machine learning
- segmentação
- dashboards
- investigação operacional
- previsão
- inferência
- storytelling analítico

A direção deve ser definida pelo GPT conforme:

- contexto
- objetivos
- limitações
- descobertas realizadas

---

## PRINCÍPIO CENTRAL

Tasks devem simular trabalho real.

O objetivo não é apenas produzir respostas corretas.

O objetivo é desenvolver:

- maturidade profissional
- pensamento estruturado
- capacidade investigativa
- autonomia
- rigor técnico
- clareza analítica
